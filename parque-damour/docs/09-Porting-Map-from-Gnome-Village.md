# Parque D'Amour: Porting Map from Gnome Village

Version 1 · 2026-10-10 · Owner: Jeduthun Oosthuis · Author: Claude (design session)

**How to use this document.** This is the line-referenced guide from the Gnome Village HTML (GV, `/root/.claude/uploads/7b9497e6-6ad3-50a2-ab24-653e6edd687e/38de409f-gnomevillage09-10.html`, 12,246 lines) to the `src/` modules of Parque D'Amour. Read `01-Decision-Register.md` (the register), `00-Product-Brief.md` and `03-Technical-Architecture.md` (the module contracts) first. Then, when a slice in `07-Build-Plan.md` tells you to write a module, find that module's row in section 2 here, read only the GV lines the row names with `sed -n`, and follow the rules of section 1. Section 3 lists GV ranges that must never be ported. Section 4 lists GV bugs that must not be carried over. Section 5 specifies the debug harness `window.__PD`. "GV 1234" is an absolute line of the GV file as indexed in `10-Gnome-Village-HTML-Architecture-Review.md` (the review); line numbers marked `~` in the review are approximate and are avoided here where a verified anchor exists. Every number, id and name here matches the register; where this document needed a value the register and `02-Game-Design.md` (the design) do not define, it is listed in section 6. The verdicts and line ranges in section 2 agree with `03-Technical-Architecture.md` section 2; if they ever differ, report it, do not resolve it yourself.

## 1. How to port

### 1.1 The four verdicts

| Verdict | Meaning | What you write |
|---|---|---|
| PORT | Copy the GV algorithm, rename, type it, remove `S`, route strings through `t()`. The rules do not change. | The GV code in TypeScript, with the header comment of 1.3 and a unit test. |
| ADAPT | Keep the GV shape (data layout, control flow, idioms) and change the rules to the design's numbers and ids. | The same shape with the design's tables substituted; the header comment lists every rule changed. |
| NEW | Nothing in GV does this. A GV line may be named as the nearest idea only. | Code from the design document named in the row; no GV copying. |
| DROP | Never ported. Listed in section 3. | Nothing. A reference to a DROP range in `src/` is a bug. |

### 1.2 The rules (apply to every PORT and ADAPT)

1. **Read only the range.** `sed -n 'A,Bp' <gv file>` for the exact lines of the row, plus at most 20 lines either side for context. Never open the whole file and never read a DROP range "to understand it".
2. **Translate to TypeScript with types.** No `any`. Typed arrays stay typed arrays. Every GV record becomes the type in 03 section 3. Every GV `let` at file scope becomes module state (rule 3). `const` tables become `readonly` tables.
3. **Replace globals with module state.** One module owns each piece of state and exports functions over it (`T`, `W`, `cam`, `visitors`, `pairs`...). Saved state has `xState()` / `setXState(s)` pairs (03 section 2). Never reach across modules through a global; import.
4. **Remove the `S` scaling (`S = 1`).** GV multiplies legacy distances by `S = 2` and `S2 = 4` at about 340 and 70 sites (GV 567, 576). One Parque tile is one GV fine tile (same `TW`, `TH`). Convert as follows, in this order of precedence: (a) if the register or the design names the number, use it; (b) else `k*S` becomes `2k`, `k*k*S2` becomes `(2k)²` written as `r*r` with `r` in tiles, bare fine-tile numbers stay as they are; (c) a GV test of the form `d2 < k*S2` (squared distance against an unsquared radius, review §16) is a GV bug: write `d2 < r*r` with `r` = the tile radius the comment intends and list it in section 6 of your own document. Never write `S` or `S2` in Parque code; `grid.ts` exports `S = 1` for the register's record only, and nothing multiplies by it.
5. **Convert time units.** GV `DAYLEN = 210`; Parque `DAYLEN = 360` (register 3.2). GV timers written in sim seconds stay in sim seconds. GV timers written in days (`T.abs + 0.7`) become the design's sim-second value. No real-time timer exists inside the simulation; audio gaps are the only real-time timers (GV `aOK` 6131).
6. **Strings to `t()`.** Every literal a player can see (toast, feed, card, rail, aria-label, status string returned by a cascade, reason for a refusal) becomes a key in `src/ui/strings/en.ts` and `es.ts` (03 section 12). Simulation code emits keys and params, never sentences. GV's inline pronoun, possessive and plural logic (`g.sex==='f'?'her':'him'`, `name+"'s"`, `n===1?' rabbit':' rabbits'`) becomes `gender()` and `plural()`.
7. **No object references in saved fields.** Every GV field that holds a record (`g.mate`, `g.home`, `g.job.b`, `g.restIn`, `c.master`, `f.home`, `b.owners`, `cam.follow`, `selected`; review §11) becomes a numeric id with 0 meaning none (03 principle P5). Render-side scratch GV wrote onto records (`g._sx`, `g._sy`, `g._ord` at 9615–9618; `b._fpc` at 7510) lives in render-side maps keyed by id.
8. **Keep the algorithm.** A PORT changes no rule. An ADAPT changes only the rules its row names. Do not "improve", "simplify" or "clean up" during the port; port, test, then change what the design says and nothing else. The one exception is a bug listed in section 4, which is fixed as that section says.
9. **Two RNG streams, as GV.** Sim decisions call `rng()`; render, audio and UI call `vrng()` (GV 583–598). GV's `flowers` scatter on the sim stream (GV 1004–1009) and `makeIR` on `Math.random` (GV 6077) are the two GV mistakes; do not repeat them. Never call `Math.random()`, `Date.now()` or `performance.now()` outside `core/loop.ts` (audio and perf read `loop.now()`).
10. **Drop the archaeology, keep the reason.** GV comments carry version tags (`v9.14`, `v9.22`) and the owner's quoted requests. Keep a one-line reason where a number is not obvious; drop the version history (review §15 item 69).

### 1.3 The header comment and the test

Every file that ports or adapts GV code starts with this comment, filled in:

```ts
// Ported from GV <first line>–<last line> (<GV function names>).
// Verdict: PORT | ADAPT. Changes: <one line per rule changed, or "none">.
// Dropped from the range: <GV lines not carried, with the section 3 row>.
```

Every exported function of a PORT or ADAPT module has a Vitest test in `tests/` that fixes at least one number from the design (for example `findPath` returns the gravel route over the lawn route when gravel costs 0.75, design section 5.5). A port without a test is not done.

### 1.4 Do not

1. Do not port a line from a section 3 range, whatever it is next to.
2. Do not read `MODE`, `PLAYER`, `cam`, the DOM or the wall clock inside `core/`, `world/`, `entities/`, `play/` or `save/` (03 principle P3; the one `MODE` read is 03 section 4.4).
3. Do not spawn particles or play cues from a `draw*` function (GV `drawSpring` 8602 and `drawWheel` 10538 did; review §2.5).
4. Do not keep a GV `DBG` flag unless 03 section 13 names it.
5. Do not keep dead GV code: review §16 lists it (`seaOver` 685, `spanFits` ~2448, `minerOf` 3073, `MK` 3837, `freeBed` 3742, `placedOf` 4123, `inbound` 4125, `retireTents` 3701, `sfxThud` 6173, `invRot` 6347 except as 2.6 says, `curOrd` 6836, `drawCabin` 7079, `WAT_F1` 9449, `ONE` 9682, `boatHomes` 11713, `pinchWorld` 11163, undo `label` 11090, the empty `if` at 11134, `W.stormT` 845, `iceCount` 1108, `g.called` 4497, `village.flightDay` 11431).
6. Do not keep a hex colour literal outside `render/ambient.ts` (brief 3.4 item 4).

### 1.5 Done when

A ported module is done when: its header comment exists; `grep -n` of every GV symbol it dropped returns nothing in `src/`; `npm run typecheck`, `npm run lint` and its tests pass; no literal string a player can see is outside `strings/`; and `determinism.test.ts` still passes.

### 5.3 Rules

1. No member mutates sim state except through `enqueue`, `apply`, `replay`, `restore`, `newPark`, `callVisitor`, `setWeather` and `simulate`. GV's `paintTile`, `setTool`, `setBrush`, `setStrict`, `setActor`, `setMode`, `jostle` style setters have no equivalent.
2. No planner, site search, or internal query is exposed (GV's `findSite`, `planEmergent`, `probeTile`, `info` and the like). A test that needs an internal queries the module through a Vitest import, not through the harness.
3. No UI function is exposed except `tap` and `pick`. Sheets, toasts and the feed are driven through the DOM in jsdom tests.
4. The object is built by spreading ten named group objects into one, so a duplicate key is impossible by construction, and oxlint `no-dupe-keys` is enabled for `src/`.
5. `body.dev` and `#dev` in the hash reveal the perf overlay and the sound check; they do not install `__PD`. Only the DEV build does (03 A20).
6. The screenshot script does not depend on `__PD` (it reads `data-day` on `body`, 03 §14), because the production build has no harness.

### 5.4 Done when

`typeof window.__PD === 'undefined'` in `dist/index.html`; in `npm run dev`, `__PD.simulate(60); __PD.hash()` returns the same value on two fresh loads of the same seed; `Object.keys(__PD).length` equals the count of members in 5.2; `__PD.apply({ side: 'park', kind: 'tool', payload: { tool: 'bench', at: { x: 10, y: 10 } } })` places a bench that `__PD.log()` then contains.

## 6. Assumptions and open points

Values this document defines that the register, the design and the architecture do not (the owner may object; on change, update `08-Test-Plan.md` and the code slice):

1. **A* heuristic scale.** The design names "octile heuristic" (§5.5). This document fixes it as octile distance multiplied by the cheapest step cost, 0.7 (flagstone), so it is admissible with closed nodes never reopened; GV used 0.45 (1472), which was below GV's cheapest step 0.30 only by accident.
2. **`OCC` is `Uint16Array`** because it holds a recycled `PropId` (03 §3.2); GV's was `Uint8Array` (631).
3. **`invRot` (GV 6347, dead in GV) is ported** into `project.ts` for the closed-form `screenToTile` (03 §7.1.6). It is the one item of the review's dead-code list that lives on.
4. **Boundary tiles are searchable** by A* (GV excluded the outer ring at 1484); only the apron and `BLOCK` are not; a gate's `outside` tile is open to the walker whose `gateIn` or `gateOut` it is. This follows design §2.3 and §5.5 but is stated here as the A* rule.
5. **The decorative songbird perch** of GV `landBird` (2293, 6303) is an `fx` event drawn by `effects.ts`, not a creature; pigeons are the only simulated birds.
6. **Snow is batched** into one path per layer, mist particles and fireflies are not ported, and the fog is a full-canvas wash (03 §7.8.2); GV drew one `fill` per flake (10098).
7. **A `debug.weather` command kind** exists in DEV builds and tests only (03 §5.1), so `__PD.setWeather` is logged and replayable.
8. **The one GV-to-Parque distance rule** of 1.2 item 4: one Parque tile equals one GV fine tile, so GV fine-tile numbers (speeds 3.4 → design 3.0, radii 0.75, 34 px) carry over unscaled and `k*S` becomes `2k` where the design is silent.
9. **Pause is not silent.** Ambience, birds and music keep playing while paused (05 §9 item 4); GV went silent (12088). Whether the waltz should keep playing on pause stays open for the Music Gate (05 §9 open point 2).
10. **Per-pair voice gating** (review §15 item 57): the limiter stays per cue kind as GV; a per-pair key for chat and laugh cues is a `cues.ts` decision for the audio slice, not a limiter change.
11. **Gardener paving time** is 1.3 s per tile from GV's `LAY_T` fallback (`||1.3` at 5167) as the design says (§11.1); GV's own `slab` time was 1.8 s. The design's number wins.
12. **`feed()` on the harness** replaces GV's `feedAll` (10702, cap 400): the harness reads the same 40 entries the sheet shows; no 400-line test log is kept.

Open points for the owner: none.
